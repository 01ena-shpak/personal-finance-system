# Ресурсна модель REST API Personal Finance System

**Статус:** DESIGN FOR MOCK API  
**Дата:** 2026-10-31  
**Архітектура:** Flet client → HTTP/JSON → FastAPI server → SQLite  
**Базова адреса для локальної демонстрації:** `http://localhost:<port>/api`

## 1. Межі контракту

REST API надає клієнту лише операції, потрібні для виконання затверджених `REQ-F-001`–`REQ-F-024`. Контракт не додає облікових записів, авторизації, мультивалютності, синхронізації, імпорту, експорту або окремого перегляду Transaction за Transaction ID.

На цьому етапі документ визначає контракт і основу для mock API. Він не є реалізацією FastAPI, бізнес-логіки або SQLite.

Загальні правила контракту:

- запити й відповіді використовують JSON;
- `Transaction ID` і `Category ID` є унікальними та незмінними ідентифікаторами ресурсів;
- поля `type` приймають лише `income` або `expense`;
- грошове поле `amount` та фінансові показники передаються як десяткові рядки UAH із двома знаками після крапки, наприклад `"1250.00"`, щоб контракт не вносив двійкової похибки;
- `date`, `date_from` і `date_to` мають формат `YYYY-MM-DD`;
- під час `POST` або `PATCH` Transaction Flet-клієнт передає поточну локальну дату пристрою User у службовому заголовку `X-Client-Local-Date: YYYY-MM-DD`; сервер використовує її лише для правила `REQ-F-005` і відхиляє відсутнє або некоректне значення;
- помилка валідації містить щонайменше `field` і `rule`, щоб Flet-клієнт міг показати поле та порушене правило;
- успішна відповідь на операцію зміни означає, що сервер успішно зберіг повний результат операції;
- сервер обробляє текстові значення лише як дані;
- назви доменних понять у документації відповідають `spec/glossary.md`.

## 2. Ресурс Category

JSON-представлення Category містить `id`, `name` і `type`. `id` відповідає поняттю Category ID, `name` — Category Name.

| HTTP | URI | Призначення та правила | REQ-ID |
|---|---|---|---|
| `POST` | `/api/categories` | Створити Category з `name` і `type`; видалити крайні пробіли з назви, перевірити непорожність, довжину до 50 символів і унікальність без урахування регістру в межах типу; присвоїти незмінний Category ID. | `REQ-F-010`, `REQ-F-011` |
| `GET` | `/api/categories` | Повернути список усіх Category з їх Category ID, Category Name і типом. | `REQ-F-012` |
| `PATCH` | `/api/categories/{category_id}` | Перейменувати Category полем `name`, застосувавши ті самі правила назви, що й під час створення; Category ID і тип не змінюються. | `REQ-F-011`, `REQ-F-013` |
| `DELETE` | `/api/categories/{category_id}` | Видалити Category, лише якщо її не використовує жодна Transaction; використану Category не видаляти. | `REQ-F-014` |

Окрема операція зміни типу Category не визначена, оскільки SRS дозволяє лише перейменування. Окремий `GET /api/categories/{category_id}` не визначений, оскільки SRS вимагає список Category, але не окремий перегляд за ID.

## 3. Ресурс Transaction

JSON-представлення Transaction для обміну містить `id`, `type`, `amount`, `date`, `category_id`, `category_name` і необов’язковий `description`. Flet-клієнт не показує `id` у Transaction List, але використовує його для редагування та видалення.

| HTTP | URI | Призначення та правила | REQ-ID |
|---|---|---|---|
| `POST` | `/api/transactions` | Створити Transaction з `type`, `amount`, `date`, `category_id` та необов’язковим `description`; перевірити допустимий тип, додатну суму з точністю до двох знаків, реальну дату не пізніше переданої локальної дати пристрою User, опис до 255 символів і відповідність типу Category; присвоїти незмінний Transaction ID. | `REQ-F-002`, `REQ-F-003`, `REQ-F-004`, `REQ-F-005`, `REQ-F-006`, `REQ-F-007` |
| `GET` | `/api/transactions` | Повернути Transaction List. Без параметрів список упорядковано за `date` від новішої до старішої. Необов’язкові query-параметри `type`, `category_id`, `date_from`, `date_to` діють як Filter окремо або разом за правилом AND; межі Date Range включні. Порожній результат подається як `[]`. | `REQ-F-002`, `REQ-F-015`, `REQ-F-016`, `REQ-F-017`, `REQ-F-018`, `REQ-F-019`, `REQ-F-020` |
| `PATCH` | `/api/transactions/{transaction_id}` | Змінити передані поля Transaction, не змінюючи Transaction ID; до повного результуючого стану застосувати всі правила створення, зокрема перевірку дати за переданою локальною датою пристрою User. | `REQ-F-002`, `REQ-F-004`, `REQ-F-005`, `REQ-F-006`, `REQ-F-007`, `REQ-F-008` |
| `DELETE` | `/api/transactions/{transaction_id}` | Остаточно видалити вибрану Transaction за її Transaction ID. | `REQ-F-009` |

Якщо `date_from` пізніша за `date_to`, сервер відхиляє Filter структурованою помилкою для Date Range, а Flet-клієнт не застосовує цей Filter і показує передбачене SRS інформаційне повідомлення (`REQ-F-018`). Якщо Transaction відсутні взагалі або не відповідають Filter, API повертає порожній масив; клієнт розрізняє ці випадки за наявністю активних Filter і показує відповідне повідомлення (`REQ-F-019`, `REQ-F-020`).

Окремий `GET /api/transactions/{transaction_id}` не визначений: відповідно до Addendum вибір запису в Transaction List дає ID для операцій редагування або видалення, але не створює нової функції окремого перегляду.

## 4. Ресурс Financial Summary

Financial Summary — read-only представлення трьох визначених глосарієм фінансових показників.

| HTTP | URI | Призначення та правила | REQ-ID |
|---|---|---|---|
| `GET` | `/api/financial-summary` | Повернути `total_income`, `total_expenses` і `current_balance` у UAH із двома знаками після крапки. Total Income охоплює всі збережені Transaction типу `income`, Total Expenses — усі типу `expense`, Current Balance є їх різницею та може бути від’ємним. Операція не приймає Filter і завжди обчислює показники за всіма збереженими Transaction. | `REQ-F-002`, `REQ-F-021`, `REQ-F-022`, `REQ-F-023`, `REQ-F-024` |

## 5. Наскрізні вимоги

Ці вимоги не потребують додаткових URI, але застосовуються до контракту й майбутньої реалізації:

| REQ-ID | Застосування в REST-контракті |
|---|---|
| `REQ-F-001` | Результати успішних `POST`, `PATCH` і `DELETE` над Category та Transaction мають зберігатися сервером між запусками системи. |
| `REQ-F-002` | `amount` і показники Financial Summary мають семантику UAH та дві десяткові позиції. |
| `REQ-NF-001` | Успішна відповідь на операцію зміни надається лише після стійкого збереження повного результату. |
| `REQ-NF-002` | Невдала операція зміни завершується без частково застосованих змін. |
| `REQ-NF-003` | За нечитабельних даних API повертає помилку, не змінюючи дані; клієнт повідомляє User. |
| `REQ-NF-004` | `name` і `description` обробляються лише як текстові дані. |
| `REQ-NF-005` | Помилка валідації містить поле та порушене правило для однозначного повідомлення клієнта. |
| `REQ-NF-006` | Клієнтські назви понять і показників відповідають глосарію; JSON використовує однозначні технічні відповідники цих понять. |

## 6. Перевірка повноти функціонального покриття

| Група вимог | Покриття API |
|---|---|
| `REQ-F-001`–`REQ-F-002` | Наскрізні правила persistence та UAH для операцій над ресурсами. |
| `REQ-F-003`–`REQ-F-009` | `POST`, `PATCH`, `DELETE` для Transaction; отримання Transaction List для відображення результатів. |
| `REQ-F-010`–`REQ-F-014` | `POST`, `GET`, `PATCH`, `DELETE` для Category. |
| `REQ-F-015`–`REQ-F-020` | `GET /api/transactions` із сортуванням, Filter, перевіркою Date Range і порожнім результатом. |
| `REQ-F-021`–`REQ-F-024` | `GET /api/financial-summary` без Filter. |

Усі `REQ-F-001`–`REQ-F-024` покриті операціями або наскрізними правилами контракту. `REQ-NF-001`–`REQ-NF-006` відображені як обов’язкові властивості майбутньої реалізації та взаємодії компонентів. BDD-сценарії `BDD-001`–`BDD-016` не змінюються: REST API надає операції та результати, потрібні для виконання описаної ними поведінки.

## 7. Підсумок операцій

- Category: створити, отримати список, перейменувати, видалити за дозволених SRS умов.
- Transaction: створити, отримати відсортований або відфільтрований Transaction List, редагувати, остаточно видалити.
- Financial Summary: отримати Total Income, Total Expenses і Current Balance за всіма Transaction незалежно від Filter.

Разом визначено 9 REST operations: 4 для Category, 4 для Transaction і 1 для Financial Summary.
