# Первинна декомпозиція SRS на тікети

Статус документа: чернетка для перевірки. Декомпозиція ґрунтується на затвердженій SRS та пов’язаних артефактах; вона не змінює baseline специфікації.

| Тимчасовий ID | Назва | Тип | Короткий опис | Пов’язані вимоги | Очікуваний результат |
|---|---|---|---|---|---|
| T-001 | Зафіксувати тип і межі користувацького інтерфейсу | Addendum | Прийняти відкладене в SRS рішення щодо типу інтерфейсу та описати спосіб доступу User до вже затверджених операцій і повідомлень без розширення функціональності. | `REQ-F-003`–`REQ-F-024`, `REQ-NF-005`, `REQ-NF-006` | Погоджений додаток до специфікації визначає тип інтерфейсу та точки взаємодії для всіх затверджених операцій. |
| T-002 | Зафіксувати механізм постійного зберігання | Addendum | Прийняти відкладене в SRS рішення щодо механізму зберігання Transaction і Category з урахуванням атомарності та поведінки при нечитабельних даних. | `REQ-F-001`, `REQ-NF-001`, `REQ-NF-002`, `REQ-NF-003` | Погоджений додаток до специфікації визначає механізм зберігання, не змінюючи вимог до постійності й цілісності даних. |
| T-003 | Реалізувати створення та список Category | Feature | Додати створення Category з унікальним незмінним Category ID, валідацією типу й назви, а також перегляд усіх Category з назвою і типом. | `REQ-F-010`, `REQ-F-011`, `REQ-F-012`, `REQ-NF-005` | Коректна Category зберігається та відображається у списку; некоректні значення відхиляються з повідомленням про поле і правило. |
| T-004 | Реалізувати перейменування Category | Feature | Додати перейменування Category із нормалізацією та перевіркою нової назви за правилами створення, без зміни Category ID. | `REQ-F-011`, `REQ-F-013`, `REQ-NF-005` | Коректна нова назва відображається у списку й пов’язаних Transaction; некоректна зміна не впливає на попередній стан. |
| T-005 | Реалізувати безпечне видалення Category | Feature | Дозволити видалення лише Category без пов’язаних Transaction і відхиляти видалення використаної Category. | `REQ-F-014` | Вільна Category видаляється; використана Category та пов’язані з нею Transaction залишаються без змін. |
| T-006 | Реалізувати створення Transaction та валідацію полів | Feature | Додати створення Transaction з незмінним унікальним ID і правилами для type, amount, date, category та необов’язкового description. | `REQ-F-002`, `REQ-F-003`, `REQ-F-004`, `REQ-F-005`, `REQ-F-006`, `REQ-F-007`, `REQ-NF-005` | Коректна Transaction зберігається; кожна некоректна комбінація відхиляється із зазначенням поля та порушеного правила. |

| T-009 | Реалізувати надійне постійне зберігання даних | Feature | Забезпечити збереження змін між штатними запусками, атомарність операцій та незмінність нечитабельних збережених даних. | `REQ-F-001`, `REQ-NF-001`, `REQ-NF-002`, `REQ-NF-003` | Після успішної операції стан відновлюється при перезапуску; збій не залишає часткових змін, а помилка читання повідомляється без перезапису даних. |

| T-011 | Реалізувати комбіновану фільтрацію Transaction List | Feature | Додати Filter за Transaction Type, Category і включним Date Range окремо та разом; некоректний Date Range не застосовувати й пояснювати повідомленням. | `REQ-F-017`, `REQ-F-018` | Список містить лише записи, що відповідають усім активним умовам; межі діапазону включені, а некоректний діапазон не змінює список. |
| T-012 | Реалізувати порожні стани Transaction List | Feature | Розрізнити відсутність збережених Transaction і відсутність збігів після фільтрації та показувати відповідні інформаційні повідомлення. | `REQ-F-019`, `REQ-F-020` | В обох випадках показано порожній список і повідомлення, що відповідає причині порожнього стану. |

## Питання для рішення перед деталізацією тікетів

Наведені питання не змінюють специфікацію й не мають прийнятих у цій чернетці відповідей.

1. Який тип користувацького інтерфейсу обрати: консольний, веб або графічний? Це прямо залишено відкладеним рішенням у SRS і впливає на деталізацію `T-001` та всіх інтерфейсних Feature.
2. Який механізм постійного зберігання обрати: файл, база даних чи інший засіб? Це прямо залишено відкладеним рішенням і впливає на реалізацію та спосіб перевірки `T-002`, `T-009` і `T-020`.
3. Як User вибирає конкретну Transaction для редагування або видалення, якщо Transaction ID не показується у Transaction List? SRS визначає внутрішнє використання ID та його невідображення, але не визначає механіку вибору в інтерфейсі.
4. Як у Filter за Category представляти дві Category з однаковою назвою, але різними типами? Такий збіг дозволений `REQ-F-011`, однак спосіб їх розрізнення в інтерфейсі не визначений.
5. Яким контрольованим способом імітувати перервану операцію та нечитабельні дані для доказів `REQ-NF-002` і `REQ-NF-003`? Це рішення потрібне для деталізації перевірки, але не є новою функцією продукту.

## Підсумок покриття

- Охоплено всі 30 затверджених вимог: `REQ-F-001`–`REQ-F-024` і `REQ-NF-001`–`REQ-NF-006`.
- Кожна вимога пов’язана щонайменше з одним тікетом реалізації або прийняття рішення та одним тікетом перевірки/валідації/gate.
- `REQ-NF-006`, для якої відсутність окремого BDD-сценарію дозволена рішенням `SPEC-GATE`, окремо покрита `T-022` і загальним `T-024`.
- Запропоновано 24 тікети: 2 Addendum, 13 Feature, 4 Test, 3 Verification, 1 Validation і 1 Gate. Штучні тікети типів Specification та Documentation не додавалися.
