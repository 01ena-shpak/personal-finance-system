# Специфікація вимог до програмного забезпечення (SRS)

## 1. Вступ

### 1.1 Призначення документа

Цей документ визначає вимоги до Personal Finance System — інформаційної системи для обліку особистих доходів і витрат одного локального User. Документ узгоджує призначення та межі системи, предметні терміни, функціональні й нефункціональні вимоги, загальні вимоги до інтерфейсів, обмеження та критерії прийняття.

SRS орієнтується на структуру IEEE 830 у спрощеному вигляді, відповідному масштабу проєкту.

### 1.2 Призначення системи

Personal Finance System призначена для ведення User особистого обліку доходів і витрат. Система дає змогу зберігати й переглядати фінансові операції, класифікувати їх за Category та визначати Total Income, Total Expenses і Current Balance.

Система розв’язує проблему незручного ручного обліку особистих фінансових операцій і полегшує розуміння поточного фінансового балансу User.

## 2. Межі системи

### 2.1 До поточної версії входить

- локальний облік фінансів одного User;
- робота з Transaction типів `income` і `expense`;
- створення, редагування та остаточне видалення Transaction;
- створення, перегляд списку, перейменування та видалення Category з урахуванням залежностей від Transaction;
- перевірка даних Transaction і Category за погодженими правилами;
- збереження Transaction і Category між запусками програми;
- перегляд Transaction List, упорядкованого за датою від новіших Transaction до старіших;
- фільтрація Transaction List за Transaction Type, Category та Date Range;
- обчислення Total Income, Total Expenses і Current Balance;
- підтримка лише валюти UAH.

### 2.2 До поточної версії не входить

- підтримка кількох користувачів, облікові записи, реєстрація та авторизація;
- мультивалютність і конвертація валют;
- окремий перегляд Transaction за Transaction ID;
- автоматичне видалення Transaction під час видалення Category;
- розширена статистика, аналітика та звіти за періодами або Category;
- імпорт і експорт даних;
- резервне копіювання;
- хмарне зберігання;
- синхронізація між пристроями;
- спільний доступ.

### 2.3 Відкладені рішення

- конкретний тип користувацького інтерфейсу: консольний, веб або графічний;
- мова інтерфейсу та інші деталі його подання;
- конкретний механізм постійного зберігання даних: файл, база даних або інший засіб.

## 3. Терміни та визначення

| Term | Визначення |

| Personal Finance System | Інформаційна система для обліку особистих доходів і витрат одного локального користувача. |
| User | Єдиний локальний користувач, який веде власний облік фінансових операцій у системі. |
| Transaction | Запис про одну здійснену фінансову операцію доходу або витрати. |
| Transaction ID | Унікальний незмінний ідентифікатор транзакції, який система створює та використовує для її редагування або видалення. |
| Transaction Type | Ознака транзакції, що має одне зі значень: `income` або `expense`. |

| Expense | Транзакція, що збільшує загальну суму витрат. |
| Amount | Додатна грошова сума транзакції в UAH з точністю не більш як до двох знаків після десяткової крапки. |
| Date | Обов’язкова дата здійснення транзакції у форматі `YYYY-MM-DD`, яка не може бути майбутньою. |
| Category | Сутність із назвою та типом, що класифікує транзакції лише відповідного типу. |
| Category ID | Унікальний незмінний ідентифікатор категорії, який створюється системою. |
| Category Name | Обов’язкова назва категорії довжиною до 50 символів, унікальна в межах її типу без урахування регістру. |
| Description | Необов’язковий текстовий опис транзакції довжиною до 255 символів. |
| UAH | Єдина валюта, у якій система зберігає та відображає суми транзакцій. |
| Transaction List | Перелік транзакцій із відображенням типу, суми, дати, назви категорії та опису за наявності. |
| Filter | Обмеження переліку транзакцій за типом, категорією або діапазоном дат. |
| Date Range | Пара початкової та кінцевої дат, що використовується для фільтрації транзакцій; початкова дата не може бути пізнішою за кінцеву. |
| Total Income | Сума `amount` усіх збережених транзакцій типу `income`. |
| Total Expenses | Сума `amount` усіх збережених транзакцій типу `expense`. |
| Current Balance | Різниця між `total income` і `total expenses` за всіма збереженими транзакціями; значення може бути від’ємним. |

## 4. Загальний опис системи

### 4.1 Контекст продукту

Personal Finance System є локальною системою для індивідуального використання. Вона не передбачає облікових записів або взаємодії кількох користувачів. Дані належать одному User і мають бути доступними між запусками програми.

### 4.2 Користувач системи

Єдиним користувачем є User — фізична особа, яка веде власний облік доходів і витрат. Спеціальні ролі або рівні доступу не передбачені.

### 4.3 Основні функції

Система підтримує керування Transaction і Category, перегляд і фільтрацію Transaction List, а також обчислення фінансових показників. Current Balance визначається як Total Income мінус Total Expenses і може бути від’ємним.

### 4.4 Дані системи

Основними сутностями є Transaction і Category. Transaction посилається на Category відповідного типу. Дані обох сутностей зберігаються між запусками програми, однак конкретний механізм зберігання цією специфікацією не визначається.

## 5. Вимоги до інтерфейсів

### 5.1 Користувацький інтерфейс

Конкретний тип користувацького інтерфейсу не визначено. Незалежно від способу подання, взаємодія User із системою охоплює операції, визначені функціональними вимогами: керування Transaction і Category, перегляд і фільтрацію Transaction List та перегляд фінансових показників.

Transaction List показує погоджені дані Transaction без Transaction ID. Інтерфейс повідомляє про порожні результати, некоректний Date Range, помилки введення та неможливість прочитати збережені дані відповідно до вимог цього документа. Назви понять, дій і показників мають відповідати глосарію.

### 5.2 Інтерфейс зберігання даних

Система повинна забезпечувати постійність даних між запусками, але формат, технологія та фізичний механізм зберігання не визначені. Вимоги до надійності та цілісності збережених даних наведено в розділі 7.

### 5.3 Зовнішні інтерфейси

Інтеграції з зовнішніми системами, імпорт і експорт, хмарне зберігання, синхронізація та спільний доступ не входять до поточної версії. Окремі апаратні або комунікаційні інтерфейси не визначені.

## 6. Функціональні вимоги

### 6.1 Загальні вимоги

- **REQ-F-001.** Система повинна зберігати дані Transaction і Category між запусками програми.
- **REQ-F-002.** Система повинна підтримувати для грошових сум лише валюту UAH і відображати суми з двома знаками після десяткової крапки.

### 6.2 Керування транзакціями

- **REQ-F-003.** Система повинна дозволяти User створити Transaction із `type`, `amount`, `date`, `category` та необов’язковим `description`, присвоюючи їй унікальний незмінний Transaction ID.
- **REQ-F-004.** Система повинна приймати `type` Transaction лише зі значенням `income` або `expense`, а `amount` — лише зі значенням, більшим за нуль, і не більш як двома знаками після десяткової крапки.
- **REQ-F-005.** Система повинна вимагати `date` Transaction у форматі `YYYY-MM-DD` та відхиляти майбутню дату.
- **REQ-F-006.** Система повинна дозволяти відсутність `description` у Transaction і приймати його довжиною не більше 255 символів.
- **REQ-F-007.** Система повинна дозволяти призначити Transaction лише Category, тип якої відповідає `type` цієї Transaction, та відхиляти невідповідну комбінацію.
- **REQ-F-008.** Система повинна дозволяти User редагувати дані збереженої Transaction зі збереженням її Transaction ID та застосовувати до змінених даних правила перевірки, визначені для створення Transaction.
- **REQ-F-009.** Система повинна дозволяти User остаточно видалити Transaction.

### 6.3 Керування категоріями

- **REQ-F-010.** Система повинна дозволяти User створити Category із назвою та типом, присвоюючи їй унікальний незмінний Category ID.
- **REQ-F-011.** Система повинна приймати тип Category лише зі значенням `income` або `expense`, вимагати її назву та приймати назву лише тоді, коли вона не складається тільки з пробілів, має довжину не більше 50 символів і є унікальною в межах типу без урахування регістру.
- **REQ-F-012.** Система повинна дозволяти User переглядати список Category.
- **REQ-F-013.** Система повинна дозволяти User перейменувати Category із застосуванням до нової назви правил перевірки, визначених для створення Category.
- **REQ-F-014.** Система повинна дозволяти User видалити Category, яку не використовує жодна Transaction, і забороняти видалення Category, яку використовує хоча б одна Transaction.

### 6.4 Перегляд і фільтрація транзакцій

- **REQ-F-015.** Система повинна відображати Transaction List із типом, сумою, датою, назвою категорії та описом кожної Transaction за наявності опису, не показуючи Transaction ID.
- **REQ-F-016.** Система повинна за замовчуванням впорядковувати Transaction List за датою від новіших транзакцій до старіших.
- **REQ-F-017.** Система повинна дозволяти фільтрувати Transaction List за Transaction Type, Category та Date Range.
- **REQ-F-018.** Система не повинна застосовувати Date Range, у якому початкова дата пізніша за кінцеву, і повинна показувати інформаційне повідомлення про некоректний діапазон.
- **REQ-F-019.** За відсутності збережених Transaction система повинна відображати порожній Transaction List та інформаційне повідомлення.
- **REQ-F-020.** Якщо жодна Transaction не відповідає активним Filter, система повинна відображати порожній Transaction List та інформаційне повідомлення.

### 6.5 Фінансові показники

- **REQ-F-021.** Система повинна обчислювати Total Income як суму `amount` усіх збережених Transaction типу `income`.
- **REQ-F-022.** Система повинна обчислювати Total Expenses як суму `amount` усіх збережених Transaction типу `expense`.
- **REQ-F-023.** Система повинна обчислювати Current Balance як різницю між Total Income і Total Expenses та допускати його від’ємне значення.
- **REQ-F-024.** Система повинна обчислювати Total Income, Total Expenses і Current Balance за всіма збереженими Transaction незалежно від активних Filter.

## 7. Нефункціональні вимоги

### 7.1 Надійність і цілісність даних

- **REQ-NF-001.** Після повідомлення про успішне створення, редагування або видалення Transaction чи Category результат операції повинен зберігатися після штатного завершення та повторного запуску програми.
- **REQ-NF-002.** Невдала або перервана операція зміни даних не повинна призводити до часткового застосування цієї операції чи пошкодження раніше збережених Transaction і Category.
- **REQ-NF-003.** Якщо збережені дані неможливо прочитати, система повинна повідомити User про помилку та не змінювати ці дані.

### 7.2 Безпека

- **REQ-NF-004.** Значення, введені User у текстові поля, повинні оброблятися лише як дані та не повинні спричиняти виконання команд або програмного коду.

### 7.3 Зручність використання

- **REQ-NF-005.** Повідомлення про помилку введення повинно однозначно вказувати поле з помилкою та порушене правило перевірки.
- **REQ-NF-006.** Однакові поняття, дії та фінансові показники повинні мати узгоджені назви в усіх частинах інтерфейсу відповідно до `spec/glossary.md`.

## 8. Обмеження

- Система призначена для одного локального User.
- Підтримується лише валюта UAH; мультивалютність і конвертація валют не передбачені.
- Облікові записи, реєстрація та авторизація не передбачені.
- Transaction може належати лише до Category відповідного типу.
- Category, яку використовує хоча б одна Transaction, не може бути видалена.
- Transaction ID і Category ID є унікальними та незмінними.
- Конкретний тип користувацького інтерфейсу, мова його подання та механізм постійного зберігання даних не визначені й не повинні виводитися з цієї специфікації.
- Функціональність, прямо перелічена в розділі 2.2, перебуває поза межами поточної версії.

## 9. Критерії прийняття

### 9.1 Загальні функціональні вимоги

- **AC-001** (`REQ-F-001`): Після створення, редагування або видалення Transaction чи Category та штатного перезапуску програми відображається останній успішно збережений стан даних.
- **AC-002** (`REQ-F-002`): Усі грошові суми зберігаються й відображаються лише в UAH із двома знаками після десяткової крапки, а використання іншої валюти недоступне.

### 9.2 Керування транзакціями

- **AC-003** (`REQ-F-003`): Після створення Transaction із коректними обов’язковими даними вона з’являється серед збережених транзакцій із введеними значеннями та унікальним Transaction ID, який надалі не змінюється.
- **AC-004** (`REQ-F-004`): Transaction з `type` `income` або `expense` і додатним `amount` із не більш як двома десятковими знаками зберігається, а порушення будь-якого з цих правил призводить до відхилення операції.
- **AC-005** (`REQ-F-005`): Transaction з обов’язковою поточною або минулою `date` у форматі `YYYY-MM-DD` зберігається, а відсутня, неправильно відформатована або майбутня дата призводить до відхилення операції.
- **AC-006** (`REQ-F-006`): Transaction без `description` або з описом довжиною до 255 символів зберігається, а довший опис призводить до відхилення операції.
- **AC-007** (`REQ-F-007`): Transaction з Category відповідного типу зберігається, а призначення Category іншого типу відхиляється без створення або зміни Transaction.
- **AC-008** (`REQ-F-008`): Коректне редагування змінює вибрані дані Transaction без зміни її Transaction ID, а некоректні нові значення відхиляються зі збереженням попереднього стану.
- **AC-009** (`REQ-F-009`): Після успішного видалення Transaction вона відсутня у Transaction List і більше не враховується у фінансових показниках.

### 9.3 Керування категоріями

- **AC-010** (`REQ-F-010`): Після створення Category з коректною назвою і типом вона з’являється у списку Category з унікальним Category ID, який надалі не змінюється.
- **AC-011** (`REQ-F-011`): Category з типом `income` або `expense` та непорожньою назвою не довше 50 символів зберігається, а порушення будь-якого з цих правил призводить до відхилення операції.
- **AC-012** (`REQ-F-011`): Назви Category перевіряються на унікальність без урахування регістру в межах одного типу, але однакова назва допускається для різних типів.
- **AC-013** (`REQ-F-012`): Список Category містить кожну збережену Category та відображає її назву і тип.
- **AC-014** (`REQ-F-013`): Коректне перейменування Category оновлює її назву у списку та пов’язаних Transaction без зміни Category ID, а некоректна нова назва відхиляється зі збереженням попередньої.
- **AC-015** (`REQ-F-014`): Category без пов’язаних Transaction успішно видаляється, а спроба видалити використану Category відхиляється зі збереженням Category і пов’язаних Transaction.

### 9.4 Перегляд і фільтрація транзакцій

- **AC-016** (`REQ-F-015`): Кожен запис у Transaction List відображає тип, суму, дату, назву категорії та наявний опис Transaction, але не відображає Transaction ID.
- **AC-017** (`REQ-F-016`): Transaction з різними датами у списку без додаткових умов розташовані від новішої дати до старішої.
- **AC-018** (`REQ-F-017`): Застосування Filter за Transaction Type, Category або коректним Date Range залишає у Transaction List лише транзакції, що відповідають вибраним умовам.
- **AC-019** (`REQ-F-018`): Date Range із початковою датою, пізнішою за кінцеву, не застосовується до Transaction List, а система показує повідомлення про некоректний діапазон.
- **AC-020** (`REQ-F-019`): Якщо збережених Transaction немає, Transaction List є порожнім і система показує інформаційне повідомлення про їх відсутність.
- **AC-021** (`REQ-F-020`): Якщо жодна Transaction не відповідає активним Filter, Transaction List є порожнім і система показує інформаційне повідомлення про відсутність результатів.

### 9.5 Фінансові показники

- **AC-022** (`REQ-F-021`): Total Income дорівнює сумі `amount` усіх збережених Transaction типу `income`, а Transaction типу `expense` не впливають на це значення.
- **AC-023** (`REQ-F-022`): Total Expenses дорівнює сумі `amount` усіх збережених Transaction типу `expense`, а Transaction типу `income` не впливають на це значення.
- **AC-024** (`REQ-F-023`): Current Balance дорівнює різниці між Total Income і Total Expenses та коректно відображається і для додатного, і для від’ємного результату.
- **AC-025** (`REQ-F-024`): Після застосування Filter, який приховує частину Transaction у списку, Total Income, Total Expenses і Current Balance залишаються розрахованими за всіма збереженими Transaction.

### 9.6 Надійність, цілісність і безпека

- **AC-026** (`REQ-NF-001`): Після повідомлення про успішне створення, редагування або видалення Transaction чи Category та штатного перезапуску програми результат операції зберігається.
- **AC-027** (`REQ-NF-002`): Після невдалої або штучно перерваної операції система містить цілісний попередній або повністю новий стан без частково змінених записів, а інші збережені дані залишаються без змін.
- **AC-028** (`REQ-NF-003`): За наявності нечитабельних збережених даних система повідомляє про помилку та не змінює ці дані.
- **AC-029** (`REQ-NF-004`): Введений у текстове поле синтаксис команд або програмного коду зберігається й відображається як звичайний текст без виконання команд чи коду.

### 9.7 Зручність використання

- **AC-030** (`REQ-NF-005`): Для кожного відхиленого значення повідомлення про помилку називає відповідне поле та пояснює порушене правило перевірки.
- **AC-031** (`REQ-NF-006`): Перевірка всіх частин інтерфейсу не виявляє різних назв для того самого поняття або дії, а назви понять і фінансових показників відповідають `spec/glossary.md`.
