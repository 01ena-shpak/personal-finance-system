# Додаток до SRS: технічні рішення та уточнення взаємодії

**Статус:** APPROVED  
**Дата затвердження:** 2026-10-16  
**Рішення прийняла:** студентка після ручної перевірки  
**Система:** Personal Finance System  
**Пов’язаний документ:** `spec/srs.md`

## 1. Призначення

Цей документ фіксує прийняті студенткою після ручної перевірки декомпозиції технічні рішення та уточнення способів взаємодії для подальшого планування реалізації. Документ затверджено 2026-10-16. Він не змінює затверджену SRS і не додає нових функціональних або нефункціональних вимог.

У разі суперечності між цим документом і затвердженою SRS пріоритет має SRS.

## 2. Цільова платформа та технології

- Цільова платформа — Android.
- Мова програмування — Python.
- Графічний користувацький інтерфейс реалізується за допомогою Flet.
- Мова користувацького інтерфейсу — українська.
- Система працює локально, без сервера та без доступу до інтернету.

Ці рішення уточнюють спосіб реалізації можливостей, визначених `REQ-F-003`–`REQ-F-024`, а також подання повідомлень і термінів відповідно до `REQ-NF-005` та `REQ-NF-006`.

## 3. Локальне зберігання даних

- Transaction і Category зберігаються в локальній базі даних SQLite.
- Доступ до SQLite здійснюється через стандартний модуль Python `sqlite3`.
- Операції зміни даних, для яких важлива цілісність кількох пов’язаних змін, виконуються в межах транзакції SQLite.
- Рішення не передбачає серверного, хмарного або мережевого компонента.

Ці рішення конкретизують реалізацію `REQ-F-001`, `REQ-NF-001`, `REQ-NF-002` і `REQ-NF-003`, не змінюючи визначеної ними поведінки.

## 4. Вибір Transaction у мобільному інтерфейсі

- User вибирає Transaction натисканням на відповідний запис у Transaction List.
- Після вибору інтерфейс надає доступ до вже визначених SRS операцій редагування або видалення Transaction.
- Для виконання операції система використовує внутрішній Transaction ID.
- Transaction ID не відображається у Transaction List або елементах користувацького інтерфейсу.

Уточнення стосується способу взаємодії для `REQ-F-008`, `REQ-F-009` і `REQ-F-015` та не створює окремого перегляду Transaction за Transaction ID.

## 5. Розрізнення Category

- Category з однаковою назвою, але різними типами `income` і `expense`, у користувацькому інтерфейсі розрізняються за типом.
- Для зв’язків із Transaction та виконання операцій система використовує внутрішній Category ID.
- Дозволена SRS унікальність назв у межах типу та можливість однакової назви для різних типів залишаються без змін.

Уточнення стосується `REQ-F-007`, `REQ-F-010`, `REQ-F-011`, `REQ-F-012`, `REQ-F-013`, `REQ-F-014` і `REQ-F-017`.

## 6. Перевірка цілісності та нечитабельних даних

- Для перевірки атомарності використовується контрольовано спричинена помилка до успішного завершення транзакції SQLite.
- Якщо операція перервалася до успішного завершення транзакції SQLite, усі незавершені зміни цієї операції повинні бути скасовані, а попередній коректний стан даних — збережений.
- Перевірка повинна підтвердити відсутність частково застосованих змін після такої помилки.
- Поведінка при нечитабельних даних перевіряється на окремій тестовій базі даних.
- Справжні дані User під час такої перевірки не використовуються і не змінюються.

Ці рішення визначають спосіб отримання доказів для `REQ-NF-002` і `REQ-NF-003`, але не додають тестових механізмів до користувацького інтерфейсу продукту.

## 7. Межі документа

Цей додаток не змінює:

- склад і зміст вимог `REQ-F-001`–`REQ-F-024` та `REQ-NF-001`–`REQ-NF-006`;
- критерії прийняття та BDD-сценарії;
- визначені SRS межі системи;
- статус затвердженої SRS.

Наведені в цьому документі рішення утворюють затверджений addendum baseline від 2026-10-16. Базова SRS залишається без змін.
