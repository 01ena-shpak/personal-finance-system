## 1. Призначення і межі

Документ пропонує нову функцію пошуку Transaction за текстом `description` лише для REST API; зміни Flet-клієнта не входять до обсягу. У чинних SRS, acceptance criteria, BDD-сценаріях та OpenAPI ця функція відсутня: `REQ-F-017` і GET `/api/transactions` визначають лише Filter за типом, категорією та діапазоном дат. До рішення `SPEC-ADDENDUM-GATE` чинний baseline не змінюється, а базова SRS не перенумеровується.

## 2. Проєкт вимоги

**ADD-L5-F-001.** REST API повинен дозволяти передати необов’язковий query-параметр `search` у GET `/api/transactions` і повернути лише Transaction, `description` яких містить заданий підрядок без урахування регістру.

- Перед порівнянням із `search` видаляються початкові й кінцеві пробіли; нормалізована довжина до застосування `casefold()` — `1..255` символів.
- Порівняння виконується як literal substring після Unicode `casefold()` для нормалізованого `search` і `description`, зокрема для коректної підтримки українського тексту.
- Відсутній `search` не застосовує пошук. `search=` або значення лише з пробілів відхиляється з `422 VALIDATION_ERROR`, `field: "search"`, `rule: "non_blank"`.
- Значення довжиною понад 255 символів після trim відхиляється з `422 VALIDATION_ERROR`, `field: "search"`, `rule: "max_length_255"`. Повторений параметр `search` відхиляється за чинним правилом одного значення query-параметра: `rule: "single_value"`.
- Transaction із `description: null` не відповідає активному пошуку.
- Символи на кшталт `%`, `_`, лапок і синтаксису команд є звичайним текстом, а не шаблоном чи кодом.
- `search` поєднується через AND із `type`, `category_id`, `date_from` і `date_to`. Сортування списку та поведінка інших Filter не змінюються.
- Відсутність збігів повертає `200 OK` і `[]`. Financial Summary, CRUD та збережені Transaction не змінюються.

## 3. Критерії прийняття

- **ADD-L5-AC-001:** пошук за literal substring повертає всі й лише ті Transaction, чиї ненульові `description` містять його після Unicode `casefold()` обох значень.
- **ADD-L5-AC-002:** одночасний пошук та чинні Filter повертають перетин усіх умов зі збереженням затвердженого сортування.
- **ADD-L5-AC-003:** відсутній параметр зберігає чинну поведінку, порожній або пробільний `search` дає контрактний `422`, а коректний пошук без збігів — `200` із `[]`.
- **ADD-L5-AC-004:** значення довжиною 1 і 255 символів приймаються; після trim значення понад 255 символів відхиляється з `422 VALIDATION_ERROR`, `field: "search"`, `rule: "max_length_255"`; повторений `search` відхиляється з правилом `single_value`.

## 5. Вплив на артефакти після затвердження

- **OpenAPI:** додати reusable query parameter `SearchFilter` до GET `/transactions`, схему `string` з `minLength: 1`, `maxLength: 255`, правила trim і literal substring через Unicode `casefold()`; додати `ADD-L5-F-001` до простежуваності операції та приклади `422` для порожнього, задовгого й повтореного значення.
- **Тести:** розширити Transaction API-тести сценаріями розділу 4 та перевірку generated `/openapi.json`; підтвердити RED до реалізації, ізоляцію SQLite і регресію чинних Filter, сортування та Financial Summary.
- **Матриця простежуваності:** додати рядок `ADD-L5-F-001 → ADD-L5-AC-001..004 → ADD-L5-P/N/B → Issue #28 → API/implementation tests → GET /transactions`.
- **Пов’язані специфікації:** після окремого затвердження узгодити acceptance criteria, BDD, API schemas, operation contract та API test scenarios без перенумерації базової SRS. Чинні документи й тікети цим DRAFT не змінюються.
- **Клієнт:** Flet та його тікети, специфікації й тести не змінюються.
